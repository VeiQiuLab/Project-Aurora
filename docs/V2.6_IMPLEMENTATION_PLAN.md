# Project Aurora v2.6 Implementation Plan

## Background

Current stable baseline:

- Project Aurora v2.4.4 Stable

Completed in v2.4.4:

- Window Extraction
- UI Component System
- Settings Architecture
- i18n Foundation
- Theme Foundation
- Runtime Packaging Fix

The current code architecture is stable. The next stage is v2.6 UI Architecture Evolution.

The v2.6 goal is to move Project Aurora from a collection of independent tool windows into a unified AI Companion application interface.

## Implementation Principles

v2.6 must follow these rules:

1. Migrate in small steps.
2. Keep each phase in a separate commit.
3. Preserve the v2.4.4 runnable state during migration.
4. Do not modify core business logic.

Do not:

- Rewrite Chat logic.
- Modify Conversation Storage.
- Modify Memory Schema.
- Modify Knowledge data format.
- Modify Remote Security Framework.

## Target Architecture

Final target:

```text
Main Window
  -> AppShell
      -> Page Router
          -> HomePage
          -> ChatPage
          -> LibraryPage
          -> MemoryPage
          -> PersonaPage
          -> RemotePage
          -> SettingsPage
```

Old windows should be gradually reused as internal page components where practical.

Example:

```text
ChatPage
  -> reuse ChatWindow logic
```

The migration should not delete old windows before feature parity is confirmed.

## Phase 0: v2.4.4 Release Verification

Status: completed.

Confirmed target:

- EXE starts normally.
- Chinese localization works.
- Chat works.
- Models works.
- Runtime packaging works.

No v2.6 work starts until v2.4.4 remains stable.

## Phase 1: AppShell Foundation

Goal:

- Create `widgets/app_shell.py`.

Scope:

- Main window layout.
- Sidebar.
- Content Area.
- Page switching mechanism.

Limits:

- Do not migrate business logic.
- Do not remove existing windows.
- Do not change Chat, Memory, Knowledge, Remote, or Conversation logic.

Risk:

- Low.

Commit:

- `Project Aurora v2.6 Phase 1 AppShell Foundation`

## Phase 2: Home Dashboard Migration

Goal:

- Convert Dashboard into a page.

Migration:

```text
main.py Dashboard UI
  -> HomePage
```

HomePage content:

- System Status
- AI Runtime
- Memory Status
- Knowledge Status
- Persona Status

Quick Actions should only keep:

- New Chat
- Open Library
- Settings

Remove from default Home:

- Diagnostics
- Developer Tools
- Test entry points

Risk:

- Low.

Commit:

- `Project Aurora v2.6 Phase 2 Home Dashboard Migration`

## Phase 3: Settings Page Migration

Goal:

- Connect existing Settings capability to the AppShell through `SettingsPage`.

Keep:

- `SettingsWindow`
- `SettingsController`
- `settings.update_many()`

Structure:

- Left: category navigation
- Right: page container that opens or hosts the existing Settings editor
- Save / Cancel remains owned by the existing Settings editor

Categories:

- General
- AI
- Persona
- Memory
- Library
- Remote
- Developer

Do not:

- Create a second settings form.
- Create a second save flow.
- Change settings keys.
- Change `config/settings.json` format.
- Start Remote services from Settings save.

Risk:

- Medium.

Commit:

- `Project Aurora v2.6 Phase 3 Settings Page Migration`

## Phase 4: Chat Page Migration

Goal:

- Connect existing Chat capability to the AppShell through `ChatPage`.

Structure:

- Left: Conversation Sidebar
- Right: Chat Area
- Top: Current Model
- Bottom: Input Area

Default view:

- Chatting.

Advanced:

- Context Inspector
- Debug Information
- Raw Prompt

Hidden by default:

- Advanced tools.

Keep:

- `ChatWindow`
- Existing streaming callbacks.
- Existing conversation operations.
- Existing context builder.

Do not:

- Copy ChatWindow business logic into ChatPage.
- Modify message schema.
- Modify conversation storage.

Risk:

- High.

Reason:

- Streaming
- Conversation
- Context
- Memory Retrieval

Commit:

- `Project Aurora v2.6 Phase 4 Chat Page Migration`

## Phase 5: Library Page Migration

Goal:

- Connect existing Knowledge capability to the AppShell through `LibraryPage`.

Structure:

- Documents
- Search
- Retrieval
- Index
- Advanced tools hidden by default

Keep:

- `KnowledgeWindow`
- `KnowledgeStore`
- Existing preview, indexing, backup, and retrieval operations

Do not:

- Copy KnowledgeWindow business logic into LibraryPage.
- Knowledge data structure.
- Metadata format.
- Vector index format.
- RAG retrieval logic.

Risk:

- Medium.

Commit:

- `Project Aurora v2.6 Phase 5 Library Page Migration`

## Phase 6: Remote Center Migration

Goal:

- Migrate `RemoteWindow` into `RemotePage`.

Structure:

- Status
- Devices
- Pairing
- Security
- Diagnostics

Keep:

- Remote disabled by default.

Do not:

- Add new Remote features.
- Enable public access.
- Change LAN API behavior.
- Change credential or token behavior.

Risk:

- Highest.

Reason:

- Security State
- LAN
- Credential
- Pairing

Commit:

- `Project Aurora v2.6 Phase 6 Remote Center Migration`

## Phase 7: Memory / Persona Migration

Goal:

- Move Memory and Persona into the unified page structure.

Keep:

- `MemoryStore`
- `PersonaStore`

Do not modify:

- Memory data structure.
- Persona data structure.
- Memory retrieval.
- Persona prompt injection.

Risk:

- Medium.

Commit:

- `Project Aurora v2.6 Phase 7 Memory Persona Migration`

## Phase 8: Legacy Cleanup

Goal:

- Clean up old UI paths after page feature parity is confirmed.

Cleanup targets:

- Old window entry points.
- Duplicate UI.
- Legacy `TEXT` usage.
- Hard-coded UI text.
- Missing Theme token usage.

Do not remove:

- Business modules.
- Storage managers.
- Data compatibility code.

Risk:

- Medium.

Commit:

- `Project Aurora v2.6 Phase 8 Legacy Cleanup`

## Per-Phase Check Standard

Every migration phase must check functionality:

- Page opens.
- Original feature still works.
- Data structure remains unchanged.

Every migration phase must check UI:

- Uses `ui_components`.
- Uses `ui_theme`.
- Does not add hard-coded fonts.
- Does not add hard-coded colors.

Every migration phase must check i18n:

- New user-visible text uses `t("key")`.
- Locale JSON files parse correctly.
- i18n key scan passes.

Every migration phase must check Git:

- One phase, one commit.
- No runtime files staged.
- Push `origin main` after commit.

## Risk Analysis

Highest risk:

- Chat
- Remote

Chat risk comes from:

- Streaming
- Conversation state
- Context construction
- Memory Retrieval

Remote risk comes from:

- Security state
- LAN status
- Credential handling
- Pairing flow

Medium risk:

- Settings

Settings risk comes from:

- Configuration save flow.
- Language refresh.
- Theme application.

Low risk:

- Home Dashboard.
- AppShell foundation.

## Recommended Execution Order

1. AppShell
2. Home
3. Settings
4. Chat
5. Library
6. Remote
7. Memory
8. Persona
9. Cleanup

## Runtime Data Rules

Never commit:

- `data/`
- `data/persona/persona.json`
- `config/settings.json`
- `.codex/`
- `build/`
- `dist/`
- `__pycache__/`
- `*.pyc`
