# Project Aurora Secure Remote Architecture

Version target: v2.5 Phase 1

This document defines the Secure Remote direction for Project Aurora. It is a design baseline only. It does not enable Remote access, change runtime configuration, or introduce public network exposure.

## Goals

- Keep Remote access disabled by default.
- Upgrade the existing Remote Framework in small, compatible steps.
- Protect every Remote and Mobile API before any non-local access is allowed.
- Support one owner with multiple trusted devices.
- Avoid multi-user account architecture in v2.5.

## Remote Mode

### Disabled

Default mode.

- No Remote service is exposed.
- LAN Chat may remain disabled independently.
- Public access is unavailable.
- Health and diagnostics can still report readiness.

Required behavior:

- This mode must be the startup default.
- Failed safety checks must force Remote back to Disabled.
- No API should assume Remote is available just because configuration keys exist.

### LAN Only

Local network access for controlled same-Wi-Fi use.

- Intended for trusted home LAN usage.
- Uses explicit user confirmation before starting LAN services.
- Does not imply public internet access.
- Must still avoid exposing sensitive APIs without authentication.

Allowed:

- LAN status page.
- Mobile Chat after explicit LAN Chat confirmation.

Not allowed:

- Public binding for remote administration.
- Unauthenticated access to private data APIs.
- Automatic firewall modification.

### Paired LAN

LAN access with trusted-device pairing.

- A device must complete pairing before calling protected APIs.
- Pairing produces a device token.
- Device token is validated by authentication middleware.
- Token metadata can identify the device label and last-used time.

This is the recommended first secure implementation step before any tunnel or public remote work.

### Secure Remote Ready

Remote is ready for secure tunnel or future public deployment, but still safety-gated.

Required before entering this mode:

- Authentication middleware enabled.
- Token storage uses Windows Credential Manager or another secure provider.
- No plaintext token storage.
- Protected API inventory completed.
- Rate limiting and audit logging available.
- Explicit user security confirmation recorded.

This mode means Aurora is prepared for secure remote transport. It does not require directly exposing Aurora to the public internet.

## Authentication Design

### Token Lifecycle

Token states:

- Not Configured
- Pending Pairing
- Active
- Revoked
- Expired

Lifecycle:

1. User starts pairing from the desktop app.
2. Aurora generates a short-lived pairing code.
3. Device submits the pairing code over LAN.
4. Aurora creates a long-lived device token.
5. Token secret is stored only through secure credential storage.
6. Token fingerprint and metadata can be kept in Remote configuration.
7. User can revoke a device token from the desktop app.

Rules:

- Pairing codes must expire quickly.
- Pairing codes are single-use.
- Device tokens must not be displayed after creation.
- Tokens must never be stored in plaintext JSON files.
- Token comparison should use constant-time comparison where practical.

### Authentication Middleware

All protected HTTP API routes must pass through one shared middleware layer.

Middleware responsibilities:

- Extract token from request headers.
- Reject missing, malformed, expired, or revoked tokens.
- Attach authenticated device metadata to the request context.
- Record authentication failures for diagnostics.
- Apply basic rate limiting.

Recommended header:

```http
Authorization: Bearer <device-token>
```

Middleware must fail closed. If credential storage or token validation is unavailable, protected APIs return an authentication error.

### API Protection Scope

Protected APIs:

- Mobile Chat send message.
- Mobile conversation list.
- Mobile conversation load.
- Mobile new conversation.
- Future Remote command APIs.
- Future settings or status APIs containing private data.
- Future Memory or Knowledge APIs.

Allowed without token only when explicitly designed:

- Local desktop GUI operations.
- Optional minimal readiness endpoint that returns no private data.

Current v2.4.x note:

- LAN Mobile APIs exist before full authentication middleware.
- v2.5 must not expand LAN or Remote exposure before API protection is implemented.

## Device Pairing

### Pairing Code

Pairing code behavior:

- Generated by desktop app after explicit user action.
- Short numeric or alphanumeric code.
- Valid for a short window.
- Single-use.
- Stored only in memory while pending.
- Never written to config files or logs.

Pairing request validation:

- Must require LAN-only source in the first implementation.
- Must check expiration.
- Must invalidate the code after success or repeated failure.

### Device Token

Device token behavior:

- Generated after successful pairing.
- Random, high-entropy value.
- Sent once to the device over the pairing response.
- Stored securely on the Aurora Windows host.
- Stored securely on the client device when possible.

Device metadata:

- Device ID
- Device label
- Created time
- Last used time
- Revoked status
- Token fingerprint, not token secret

### Credential Manager Storage

Windows Credential Manager should be the first secure storage provider.

Storage rules:

- Store token secrets in Credential Manager.
- Store only non-secret metadata in `data/remote/remote.json`.
- Keep diagnostics separate from real token operations.
- Never fall back to plaintext token files for enabled Remote modes.

If Credential Manager is unavailable:

- Secure Remote Ready must be blocked.
- Pairing must not complete.
- UI should explain the storage problem and keep Remote disabled.

## Security Rules

Mandatory rules:

- Remote access is disabled by default.
- Public access is unavailable unless safety checks pass.
- No plaintext token storage.
- No unauthenticated protected API exposure.
- No multi-user account system in v2.5.
- No automatic firewall changes.
- No automatic public tunnel creation.
- No privileged system command API.
- No Memory, Knowledge, Conversation, or Settings API exposure without authentication.

Operational rules:

- Authentication failure should not leak whether a device ID exists.
- Logs must not include token secrets or pairing codes.
- Remote readiness checks must be visible before enabling Remote.
- Safety Gate must fail closed.
- Existing LAN Mobile Chat behavior must remain backward compatible until authentication is intentionally enforced.

## Migration Plan

### Current Framework

Existing components:

- `modules/remote.py` manages Remote state, safety gate, LAN readiness, diagnostics, and URL previews.
- `modules/authentication.py` reports authentication configuration state.
- `modules/credential_storage.py` tests Windows Credential Manager availability with a test credential.
- `modules/lan_server.py` provides LAN status and Mobile Chat HTTP routes.
- `modules/mobile_chat.py` checks Remote and LAN Chat enabled state before chat requests.

Current limits:

- Authentication is configuration/status-oriented.
- LAN HTTP routes do not yet use shared request authentication middleware.
- Credential storage diagnostics do not yet store real device tokens.
- Public Remote is intentionally not implemented.

### Step 1: Auth Middleware Foundation

- Add shared request authentication middleware.
- Keep Remote disabled by default.
- Protect Mobile conversation and Mobile Chat APIs behind a feature-gated policy.
- Add audit records for accepted and rejected requests.

### Step 2: Pairing Workflow

- Add desktop pairing action.
- Generate short-lived pairing code.
- Add pairing endpoint limited to LAN.
- Create device token after successful pairing.
- Store token secret in Credential Manager.

### Step 3: Device Management

- Show paired device list in desktop UI.
- Support revoke device.
- Show last-used time and status.
- Keep single-owner, multi-device model.

### Step 4: Secure Remote Readiness

- Add readiness checks for middleware, token storage, paired device, audit logging, and rate limiting.
- Keep direct public exposure blocked.
- Prepare for secure tunnel integration such as Tailscale without implementing it as an automatic dependency.

### Step 5: Compatibility Transition

- Preserve existing LAN Chat routes.
- Introduce authentication warnings before enforcement.
- Allow users to pair devices before requiring tokens.
- Do not migrate Conversation, Memory, Knowledge, Persona, or Remote data structures unless a future phase explicitly requires it.

## Non-Goals for v2.5

- Multi-user accounts.
- Public internet hosting.
- Automatic tunnel setup.
- Voice or Live2D remote control.
- Remote file browser.
- Remote system command execution.
- Replacing the existing Remote Framework.
